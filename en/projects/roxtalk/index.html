Problem & context

RoxTalk began in 2025 as an individual prototype bringing conversations, profiles, and stories together in a welcoming, adaptable interface. The 2026 revision addresses what surrounds a message: who can send it, how it is confirmed, and what happens after a reload or a network interruption. Next.js and MongoDB support the HTTP journey; Socket.IO extends communication in environments configured for that transport.

My contribution

I developed the interface, API connections, authentication and communication contexts, and the prototype's data models. I wanted a simple place for people to express themselves, where each profile and conversation had context. The 2026 revision connects that purpose with opaque sessions, idempotent sends, persisted read state, and HTTP recovery, making storage and deployment limits explicit.

01

Start with a person

Profiles bring together a name, avatar, and biography, while the contact list opens a conversation. These elements give context to the person behind each message.

02

Conversations with context

History and unread messages rely on persisted state. Sending distinguishes waiting from server confirmation, while HTTP queries retrieve updates when returning to the view or recovering network access. Presence is queried over HTTP; typing notifications use Socket.IO when configured.

03

Share a moment

Stories combine text, images, and audio notes, with reactions and expiration. The code supports file selection and includes camera capture and voice recording according to browser capabilities and permissions.

04

An experience that adapts

Access, contacts, conversation, and story views share interface components. Their layout adapts to the available width to preserve readability and access to actions on mobile.

01

Shared contracts across views

TypeScript defines users, messages, posts, and events. React contexts coordinate authentication and communication, while reusable components provide a common foundation across views.

02

A session that establishes identity

The HttpOnly cookie contains an opaque token; MongoDB retains its hash, user, and expiration. APIs derive identity from that session and restrict conversations and media to authorized people. The Socket.IO server rechecks sessions and handles revocation.

03

Save once, recover later

Each send carries a clientMessageId with a unique index per sender; retrying a request returns the saved message. Confirmations return the persisted record, while read state and paginated history remain in MongoDB to reconstruct the conversation after a reload.

04

HTTP as the foundation, optional Socket.IO

The interface sends and queries messages over HTTP, with periodic updates and recovery when returning to the view or regaining network access. In environments with a configured Socket.IO server, the same message service provides acknowledgements, presence, and typing notifications. The HTTP experience does not require a WebSocket connection.

05

Limits on shared content

The server checks format, file contents, and size: up to 500 KiB per image or audio file, four images, and 2 MiB combined. Media currently lives in MongoDB documents and is served through authorized endpoints. Moving it to object storage is a next step; stories retain their expiration date.

Next steps
